# Avery Goal 模式工程参考

调研日期 2026-11-17。本文记录 Claude Code 公开机制、Avery 当前实现与建议的工程验收标准，供后续设计和实现使用。

## 实现记录

- 内置 Stop hook 在候选和工具协议已保存后触发，独立审核返回达成、反馈或暂停。Trace 以同一候选步骤 ID 关联钩子与审核。
- 显式继续目标先触发续跑审核。它使用上次候选、当前用户补充和已有回执。最终达成仍由本次交付审核决定。无正文的继续动作不会写成用户消息。
- 对话保存续跑审核和交付审核的状态及可展示理由。暂停期间的迟到结果会被丢弃；重启后按最近已保存的预算和目标状态恢复。
- 已通过 13 项 Goal 集成测试，验证 Stop hook 交付候选、审核反馈进入下一次执行模型请求、桌面路由暂停与继续、修改后使用新目标、删除后重启不恢复，以及审核中断和浏览器写入幂等。集成测试经过实际 Host、Kernel 和 Provider 序列化，使用受控 SSE 响应；远端模型的判定质量仍按本文的效果评估部分验证。

## 1. Claude Code 的公开机制

### 完成条件与审核边界

Claude Code 的 `/goal` 将用户给出的完成条件绑定到当前会话，一个会话同时只有一个活动目标。设定目标后立即开始回合。执行 Agent 准备结束回合时，会话级的 prompt-based `Stop` hook 把条件和对话证据交给独立的审核请求。审核返回达成、继续或不可达及简短理由。继续时将理由交给执行 Agent，达成或不可达时结束目标并保留相应记录。用户中断与 API 失败有各自的生命周期，普通 `Stop` 不负责这两类终止。`/goal` 沿用已有工具权限。 [Claude Code Goal 文档](https://code.claude.com/docs/en/goal#how-evaluation-works) · [Stop 与 StopFailure](https://code.claude.com/docs/en/hooks#stop)

审核使用当前供应商配置的小型快速模型，可由 `ANTHROPIC_DEFAULT_HAIKU_MODEL` 调整。审核请求无工具权限，依靠执行端提供可核对的证据。官方文档因此建议把目标写成可观察的终态、核验方法和必要约束。通用 hooks 还支持脚本或可调用工具的审核 Agent，属于另行配置的验证方式。官方只定性描述审核用量通常较小，未给出通用 Token 数或比例。 [审核模型与费用](https://code.claude.com/docs/en/goal#evaluation-model-and-cost) · [Hooks 指南](https://code.claude.com/docs/en/hooks-guide#prompt-based-hooks)

### 恢复、失败与可观测性

| 工程问题 | Claude Code 公开行为 |
| --- | --- |
| 会话恢复 | 各恢复入口都恢复仍活动的目标。恢复时重置该次会话的计时、回合计数和 Token 基线。用户可查询或清除目标。 |
| 短暂故障 | 交互模式支持对部分短暂错误自动重试，最多三次后暂停。限流、用量耗尽等情况按错误类型等待或暂停。文档还区分需要修复后重新设定目标的失败。 |
| 后台工作 | 后台 shell 或子 Agent 在运行时推迟审核，结果返回后再进入回合。默认首次检查在等待 30 分钟后，后续间隔增至 1 小时和 2 小时。用户两次输入之间最多主动发起 3 次空闲检查。 |
| 无进展 | 通用 `Stop` 默认允许连续续跑 8 次，下一次阻止结束的结果会被覆盖。工具调用重置该计数。目标可保留，等待下一条用户消息恢复。 |
| 审核记录 | 对话展示每次判定，状态面板展示最近理由、耗时、审核回合和用量。非交互运行可输出流式事件。 |

### Anthropic 的长任务工程实践

- 跨上下文恢复时保存可核对的进度、产物和下一步。新回合应能从可信状态继续，避免重新探索或过早宣布完成。 [Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- 让执行和评分成为独立请求，并给审核者可判定的标准。Anthropic 的应用开发研究还用分阶段验收条件约定可交付结果，并用固定示例校准评分。该实验的审核 Agent 能独立打开页面，Claude Code 内置 `/goal` 的审核只读其输入。 [Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps)
- 对可机器验证的结果使用确定性校验，模型判断用于语义和质量。端到端测评读取真实结果状态，配合人工标注校准审核器。 [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 2. Avery 的基线

### 已有能力

- Host 持久化目标和冻结的审核配置。优先使用次级模型，未配置档次时以当前执行模型发起独立审核请求。审核低思考强度、无工具权限、校验结构化结论和证据引用。
- Kernel 在执行模型返回无工具调用的候选答复时调用审核。审核要求补齐缺口时继续当前 Run，遇到已授权操作的结果未知时保留核对门槛。Hook 所需的交付控制点已经存在于 Kernel，Host 负责 Goal 状态和持久化。
- 当前配置为累计活跃 3 小时、执行与审核合计 2,000 万 Token（按供应商报告计量）、单次审核最多 3 分钟。现有 6 次审核上限与连续三次相同缺口停下来是额外约束。审核请求总预算取模型上下文窗口与 16,000 Token 中的较小值，包含最多 1,200 Token 的输出预算和 512 Token 的预留空间。

## 3. 推荐的生命周期

### 入口与状态归属

让 Host 收到明确的开始、继续、暂停、取消、编辑动作。保留 `goalId` 作为生命周期身份，`requestId` 仅标识本次执行尝试。目标携带目标版本、用户约束、审核配置及预算。修改完成条件时提高目标版本，重新核对旧证据的适用性。

| 入口或事件 | 推荐处理 |
| --- | --- |
| 新建目标 | 保存原始目标，拆成少量可核验且有稳定 ID 的要求。必要条件不清楚时先问用户。完成条件清楚时直接执行。 |
| 点击「继续目标」 | 通过专用 Host 动作进入原目标，以目标 ID 和预期版本防重。无补充文字时只记录控制事件。 |
| 目标等待用户补充 | 将输入框默认动作明确显示为「回复并继续目标」，把真实补充追加一次。保留用户主动选择普通对话的入口。确认卡和问答卡继续使用各自原有协议。 |
| 原确认或问答结算 | 先恢复原工具调用的协议和结果，核对权限及幂等账本。会改变外部状态的待执行确认仍按原确认交互处理。 |
| 续跑前 | 用目标要求、上次候选、失败或等待原因、已知证据及最新用户补充生成审核输入。此阶段可处理尚无候选正文的目标。审核返回下一步、仍需用户或当前阻塞。已有证据看似达成时，执行 Agent 回读状态后再交付。 |
| 执行 Agent 提交候选 | 在工具结果已结算的交付边界运行正式审核。该版本的所有必需条件通过后，Host 才发布目标达成。缺口反馈进入原 Goal 的下一次执行。 |
| 工具尚未结算或外部结果未知 | 保留等待或人工核对状态。浏览器恢复优先重新观察当前页面，检查上次操作证据，再推进剩余工作。 |
| 暂停、取消、重启 | 记录明确的状态和原因。使旧调用的迟到结果失效。重启后从已提交的检查点恢复，核对仍未结算的外部操作。 |

执行流程为 **接收目标 → 执行 → 候选交付 → 审核 → 达成、续跑或等待**。用户再次继续时，从已提交的检查点先做续跑前审核。若环境状态只有浏览器重新观察才能确认，续跑前审核可要求执行 Agent 先观察，正式验收仍须引用随后获得的证据。审核反馈只提供缺口和所需证据，操作授权继续由用户、权限策略和账本决定。

状态迁移区分执行中、审核中、可继续的等待或暂停、达成、不可达和取消。等待状态带上对应的恢复条件，例如回答问题、提供授权或核对外部结果。审核失败、超时、预算耗尽和模型判断不可达各有原因码。恢复动作只有在匹配原因和目标版本时才进入下一阶段。

### 检查点与并发

- 检查点至少记录目标 ID 与版本、当前尝试、状态和原因、上次候选及其证据、待处理交互、累积预算、权限引用和最后一次审核。审核身份由目标版本、阶段和候选或检查点版本确定；重复 IPC、双击和重试应归并到同一审核。
- Host 串行处理同一会话的目标状态变更，提交时核对目标版本、尝试和审核身份。候选、接受的结论、状态与可重放的展示事件需要有一致的提交边界。若当前存储跨库，先提交权威 Goal 记录，再以同一事件 ID 幂等投影到会话展示，启动时补齐漏投影的事件。
- 崩溃发生在审核请求发出后、提交前时，将旧审核尝试记录为中断。满足预算和权限前提后，可以重新审核同一证据。工具已经结算时复用回执。对提交、上传、消息等结果未知的动作，先对账，避免自动补发。
- 旧记录按版本兼容读取。历史中已有 Goal 证据继续可查；缺少稳定回执、目标版本或真实环境结果的记录，续跑时要求补证。编辑目标后，已完成的实际副作用仍可通过账本查询。

## 4. 消息、证据与预算

### 消息只保留一个来源

1. 真实用户文字由用户消息 ID 标识。重试绑定原消息与失败尝试，IPC 幂等键沿同一提交延续。新发送使用新消息 ID，文本相同也视为独立用户意图。两条旧请求已经写入时保留历史，通过已知重试关系治理后续模型投影。
2. 目标条款、动态上下文、运行提醒和审核反馈使用不同的元数据。目标条款只从当前目标版本投影一次；提醒按用途携带最新状态；审核反馈按审核 ID 注入一次。压缩、重试与跨 Run 恢复都使用同一组装逻辑。保留真实用户补充、已完成工具协议和证据索引。
3. 对话持久化、模型投影和审计记录各自使用稳定来源 ID。供应商适配如需要 `user` 角色承载内部数据，由适配层转换。程序判断授权、用户回合和重试身份时读取元数据。

### 确定性验收与模型审核

| 场景 | 宿主提供的证据 | 审核模型判断 |
| --- | --- | --- |
| 简历匹配与优化建议 | 用户授权的简历版本、JD、候选文本及可定位的原文引用 | 匹配结论是否有据，建议是否针对实际缺口，是否把推测写成事实 |
| 编写或保存简历 | 档案资料版本、交付文本；用户要求保存时再提供实际保存回执和回读版本 | 文本是否体现岗位需求、事实是否来自授权资料、内容是否完整 |
| 网申填写与核对 | 同一任务页的当前状态、字段读取、校验结果及未处理项 | 表单语义与用户资料是否一致，缺口应由执行端还是用户处理 |
| 用户授权的最终提交 | 对应目标和资源的成功回执，加上状态页或申请记录的独立证据 | 必需字段和约束是否符合。提交发生与否由宿主依据回执和状态核验 |

为每条完成要求固定 ID、证据类型和所需验证。Host 校验每项都覆盖、引用可查且匹配目标版本、资源和动作语义。当前审核器已经校验证据引用及一组成功工具；细化到每项后，读到资料、填写成功或页面表面显示通过，都只能证明各自的那一步。审核模型不能通过省略必需项，或把外部动作改判为文本项，让目标达成。

例如目标是「填好该岗位网申中的已知字段，核对后交给我确认」，可以定义三条要求。已知必填字段有来源及回读，缺失信息列清单并说明需要谁处理，提交控件留给用户确认。前两条引用表单校验和来源，第三条依据动作账本与待确认状态。若用户另行授权提交，才新增提交结果的验收要求。

审核输入由宿主投影出最小证据包，优先保留必需要求的候选、当前回读、真实回执和用户澄清，限制网页、简历正文和自由文本体积。保留证据指针，证据不足时明确返回缺口。网页、工具返回和文档文本按不可信数据处理；跨供应商审核时遵守数据授权配置。对小模型使用固定结构和少量已标注样例校准，区分模型不支持、返回格式错误、证据超长、调用超时以及审核判定未达成。

### 预算与停机

- 沿用当前用户设定的三个上限。按目标 ID 累加活跃时间与执行、审核用量，暂停或等待用户的时间独立记录。每次续跑、模型请求、工具批次和自动重试前检查剩余额度。审核截止时间取 3 分钟、剩余目标时间和传输层限制中的最早有效截止时间。
- 供应商报告通常在请求结束时取得。入场时按估计为新请求预留空间，回传后结算实际用量。缺失用量单独计数并采用清晰的估算或暂停规则，区分已报告用量和估计。发布前锁定超限边界、崩溃回收预算及同一审核重试的计数口径。
- 暂保留 6 次审核与连续三次相同缺口上限。续跑前审核纳入总预算，埋点区分正常交付审核、续跑前审核和传输重试，再依据真实任务样本判断是否需要分别限额。
- 短暂网络错误可以有界重试；登录、页面接管、权限拒绝或结果未知交给对应等待状态。按稳定要求 ID、缺口 ID 和真实证据变化判定进展。重复读页、变更调用 ID 或改写描述不刷新空转计数。后台定时检查可待生命周期和幂等链路验证后再决定是否引入。

## 5. 对话展示与验收

### 可观测性

对话过程用可展开的条目显示「续跑前审核」和「交付审核」，展示审核状态、结论、关键缺口及可核对的证据摘要。Goal 面板显示当前阶段、上一结论、审核次数、累计活跃时间、已报告用量和剩余预算。应以 Host 接受并持久化的记录作为恢复来源。

每条审核记录至少包含 `goalId`、目标版本、`requestId`、`reviewId`、审核阶段、模型与供应商、状态和原因码、耗时、Token 用量、缺失用量标志及证据 ID。表单原值、联系方式、完整简历、认证信息和审核模型的内部推理无需进入默认 Trace 或对话展示。错误应能定位到执行、工具结算、证据投影、审核请求或审核校验阶段。

### 实现顺序与发布验收

| 阶段 | 必须验证的结果 |
| --- | --- |
| P0 入口与消息身份 | 重现最近会话的失败重试、浏览器恢复后补充、无文本继续。一次提交只产生一条真实用户消息；补充和按钮都能关联同一 Goal；用户明确选择普通对话时单独运行。 |
