# 中国企业 ATS 岗位采集 POC 方案与要求总结

## 一 方案结论

第一阶段优先实现北森 `BeisenCareerAdapter`，同时将 Moka `MokaPublicAdapter` 列为 P0，通过企业面向求职者公开的招聘页面及接口获取岗位，统一标准化、去重、识别变化并入库，供求职 Agent 匹配使用。

POC 要证明一套适配器能够稳定服务多家企业，重点是数据可信、失败隔离和维护成本可控。第一版不追求全量企业覆盖，也不接入需要登录、权限绕过或私有协议逆向的数据源。

原文引用的校园招聘 Source Registry 样本包含 164 家启用企业，其中 Moka 约 40 多家、北森约 79 多家，合计约占该工程样本的 75%。这属于工程样本分布，不代表中国 ATS 市场份额。

## 二 目标与范围

验证四项能力：识别企业招聘站的 ATS 类型；获取职位 ID、标题、地点、职位描述和更新时间等结构化字段；识别岗位新增、更新与关闭；在单个企业来源失败时继续处理其他来源。

| 平台 | 第一阶段采集方案 | 关键要求 |
| --- | --- | --- |
| 北森 | 识别 `*.zhiye.com`、`*.italent.cn` 及页面特征；读取 `/portal/registerSystemInfo`；调用 `/api/Jobad/GetJobAdPageList` | 提取 `PortalId`，完成分页、字段转换和快照完整性判断；覆盖自定义域名场景 |
| Moka | 识别 `*.mokahr.com` 及 `campus-recruitment`、`social-recruitment`、`apply` 路径；优先使用文档公开的招聘 Job API | 提取租户、`orgId` 和招聘类型；支持校园招聘与社会招聘；自定义域名作为后续识别扩展 |

原文将 `GET /api-platform/v1/jobs/{orgId}` 列为 Moka 的概念接口示例，或采用租户仍支持的公开 Job API。具体路径、参数、匿名访问能力应在接入时确认。

第一阶段排除微信公众号、BOSS 直聘、猎聘、智联招聘、前程无忧，以及需要扫码、个人 Cookie、登录身份或企业 HR 授权的数据源。不处理验证码、私有签名、WAF 绕过或 Moka 私有加密协议。

## 三 核心架构与数据约定

处理链路为：企业招聘 URL → 来源发现 → ATS 识别 → 北森或 Moka 适配器 → `NormalizedJob` → 去重与 Diff → Job Store → 求职 Agent。

### 来源管理

所有企业来源进入统一 Source Registry，记录来源 ID、企业 ID 与名称、招聘 URL、ATS 类型、采集方式、健康状态、快照状态、最近探测时间、最近成功时间、最近岗位数及启用标记。

三类状态应分开记录：

| 维度 | 原文建议值 | 含义 |
| --- | --- | --- |
| `health` | `healthy`、`partial`、`timeout`、`schema_changed`、`access_controlled`、`empty`、`unsupported` | 来源本次访问及解析情况 |
| `snapshot_status` | `complete`、`partial`、`unknown` | 本次岗位集合的完整性 |
| `transport` | `public_api`、`public_portal_json`、`browser`、`unsupported_private_api` | 实际采集方式或不支持原因 |

能抓到岗位不等于完整遍历；`partial` 快照是正常状态，不能一律视为采集失败。

### 统一岗位模型

最低数据契约为 ATS 职位 ID、标题、企业和来源 URL。统一模型还应包含内部 ID、来源 ID、ATS 类型、部门、地点列表、岗位类型、职位描述、任职要求、薪资、发布与更新时间、申请 URL、内容哈希及首次和最近发现时间。

岗位 ID 建议使用 `{ats_type}:{tenant}:{ats_job_id}`。对标题、职位描述、任职要求、地点和部门计算 `rawHash`，用于识别内容变化。

缺失字段保留缺失状态，不伪造职位描述，也不从描述猜测任职要求。不完整或解析异常的岗位可进入 `job_quarantine`，保存来源、职位 ID、原因、原始数据和时间。

### 接口与存储

适配器提供 `probe(source)` 和 `collect(source)`。采集结果统一返回来源 ID、健康状态、快照状态、标准化岗位及错误信息。

建议分别保存 `jobs`、`source_runs` 和 `job_quarantine`。Source Runner 为每个来源单独设置超时并捕获异常，批量运行通过结果隔离保证单来源失败不终止整个批次。

## 四 两类适配器的实现重点

### 北森

1. 根据域名及 HTML、页面资源、`BSGlobal` 等特征识别平台。
2. 请求 `GET /portal/registerSystemInfo`，提取 `PortalId`、`Name`、`Key`，其中 `PortalId` 是列表请求的关键字段。
3. 请求 `POST /api/Jobad/GetJobAdPageList`，携带 `PageIndex`、`PageSize`、`PortalId` 等字段。
4. 将 `JobAdId`、`JobAdName`、`LocNames`、`Duty`、`Require`、`Salary`、`ChangeDate` 和 `PostDate` 等转换为统一模型。
5. 默认每页 50 条。遇到空页、记录不足一页、已达到响应中的 `Count` 或达到页数上限时停止；默认最多 20 页，可配置为 5、10、20 页。

缺少 `PortalId` 时标记 `schema_changed` 并返回空结果，避免异常影响其他企业。达到页数上限但尚未取完时，应保留部分快照语义。

### Moka

1. 从招聘 URL 解析租户、`orgId` 和 `campus` 或 `social` 类型。
2. 使用公开招聘 Job API，原文建议 `limit=50`、`status=open`，采用 `limit/offset` 分页。
3. 按接口实际支持情况使用招聘类型、关键词、状态和更新时间区间过滤；后续同步可基于最近成功同步时间减少请求。
4. 若只能使用 `/api/outer/ats-apply/website/jobs/v2` 等私有加密接口，返回 `health=unsupported`、`transport=unsupported_private_api`，第一版不进行解密或逆向。

## 五 快照与岗位变化规则

| 事件 | 判定条件 | 后续处理 |
| --- | --- | --- |
| `NEW` | 当前岗位 ID 不在既有岗位集合中 | 入库并进入匹配流程 |
| `UPDATED` | 岗位 ID 相同，内容哈希不同 | 更新岗位；关键字段改变时重新匹配 |
| `UNCHANGED` | 岗位 ID 与内容哈希均相同 | 记录本次发现情况 |
| `CLOSED` | 当前快照为 `complete`，此前岗位本次缺失 | 标记关闭 |

**部分或未知快照绝不触发 `CLOSED`。** 例如昨日有 A、B、C，今天部分抓取只得到 A、C，不能认定 B 已关闭。来源访问失败、超时或返回空结果，也不能直接用来推断岗位关闭。

原文建议：岗位连续 30 天未见，且没有完整快照证明其消失时，标记为 `stale` 并继续验证，不直接关闭。

新增岗位立即进入匹配流程；更新岗位仅在标题、地点、职位描述、任职要求或部门等关键字段改变时重新匹配。采集层负责事实数据，Agent 负责理解与匹配；LLM 不猜测职位 ID、发布日期或关闭状态。

## 六 请求控制与错误处理

采集仅限企业主动公开的招聘信息，使用最小必要请求、明确的 User-Agent、访问节流和超时控制。

| 项目 | 原文建议默认值或规则 |
| --- | --- |
| 单次 HTTP 超时 | 10 秒 |
| 单来源总超时 | 30 秒；超时后停止该来源并继续其他来源 |
| 同一 Host 请求间隔 | 300–500 毫秒 |
| 单 Host 最大并发 | 2 |
| 全局最大并发 | 10；POC 可保守设置为 5 |
| 重试次数与退避 | 最多重试 2 次，间隔 1 秒、3 秒 |
| 可重试情况 | 429、502、503、504、网络超时、连接重置 |
| 停止且不重试 | 401、403、验证码、要求登录、要求签名或明确访问控制 |

统一错误代码包括 `SOURCE_TIMEOUT`、`SOURCE_401`、`SOURCE_403`、`SOURCE_CAPTCHA`、`SOURCE_LOGIN_REQUIRED`、`SOURCE_SCHEMA_CHANGED`、`SOURCE_EMPTY`、`SOURCE_PAGE_LIMIT`、`SOURCE_PARSE_FAILED`、`SOURCE_PRIVATE_API` 和 `SOURCE_NETWORK_ERROR`。

## 七 回归测试与验收

建立固定 50 家企业回归集：25 家北森、25 家 Moka。样本同时包含成功、失败、部分快照、大小招聘站、标准 ATS 域名及自定义域名，不能只选择成功来源。

| 验收项 | 要求 |
| --- | --- |
| 北森岗位提取率 | 固定 25 家中至少 60%，即至少 15 家能返回一个或以上结构化岗位 |
| Moka 岗位提取率 | 固定 25 家中至少 60%，即至少 15 家能返回一个或以上结构化岗位 |
| 岗位最低质量 | 包含 ATS 职位 ID、标题、企业和来源 URL；尽可能保留地点、描述、要求与更新时间 |
| 快照安全 | `partial` 和 `unknown` 不生成关闭事件 |
| 批次隔离 | 单来源失败不影响其他来源 |
| 访问边界 | 不绕过 401、403、验证码、登录或私有加密接口 |
| 请求控制 | 所有请求有超时，节流和重试规则生效 |

北森测试至少覆盖正常获取、`PortalId` 缺失、岗位数小于及大于 50、多页、页数上限、空结果、超时、结构变化和自定义域名。

Moka 测试至少覆盖校招与社招、公开 API 成功、空岗位、超时、公开列表缺失、任职要求缺失、私有加密接口和自定义域名。

两个平台均达到 60%，且快照安全与批次隔离通过，才进入 Production MVP。原文提出提取率低于 40% 时重新评估 ATS 优先策略。

## 八 运行记录与监控

每次来源运行记录来源 ID、ATS 类型、采集方式、起止时间、耗时、请求数、接收与标准化岗位数、隔离岗位数、新增、更新、关闭数量，以及快照状态、健康状态和错误代码。

监控至少包含来源探测成功率、岗位标准化成功率、来源延迟 P50/P95、每来源岗位数、部分快照比例、结构错误率和超时率；北森与 Moka 成功率单独统计。

最终 50 家回归报告按平台列出成功、部分和受阻来源，并汇总岗位数量、字段完整率、延迟及错误分布。

## 九 实施里程碑与后续扩展

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 1 基础框架 | Source Registry、ATS Detector、NormalizedJob、基础适配器和 Source Runner | 静态 Fixture 测试通过 |
| 2 北森适配器 | 租户识别、PortalId、列表、分页、标准化及快照状态 | 固定 25 家达到至少 60% 提取率 |
| 3 Moka 适配器 | 公开招聘 Job API、分页和标准化；私有接口明确标记不支持 | 固定 25 家达到至少 60% 提取率 |
| 4 变化检测 | Diff Engine 及新增、更新、关闭事件 | 包含部分快照绝不关闭岗位的测试 |
| 5 综合回归 | 运行固定 50 家并输出报告 | 汇总提取率、数据质量、延迟和错误分布 |

POC 通过后扩大到 100 家：50 个 ATS 来源和 50 个非 Moka、非北森来源。实际效果按“ATS 覆盖率 × 适配器成功率 × 岗位覆盖率”评估，不使用厂商市场份额代替验证。

第二阶段候选为飞书招聘、Hotjob／大易和大型自建招聘站，按新增可覆盖企业数与开发维护成本决定优先级。采集方式优先级为公开 API、公开 Portal JSON、HTML、浏览器；浏览器采集单独标记。飞书招聘仅考虑公开求职者招聘站，不使用企业 Tenant Token API 或签名逆向。

## 十 实现前需明确的事项

以下事项来自原文的示例、未定义部分或字段约定，需要在实现时明确：

- **Moka 接口可用性：** 原文提供概念路径及参数，需逐租户确认公开接口是否可匿名访问、支持哪些字段和分页方式。
- **增量同步的完整性：** 仅按更新时间获取变化岗位不代表完整岗位集合，不能据此将未返回岗位关闭。应明确完整同步与增量同步各自的快照标记。
- **岗位状态枚举：** 原文存储状态列出 `open/closed/unknown`，TTL 又使用 `stale`，需要统一数据模型。
- **边界验收结果：** 原文未定义 40% 至不足 60% 的处理方式，应在验收前明确是否继续改进、补测或调整范围。
