## 3. 审查发现

### R-01【P1】幂等回放写盘失败会导致已成功的业务写入被重复执行

相关位置：

- `apps/backend/src/router.ts`：先执行 `Resolve(channel)(...args)`，再调用 `idempotencyStore.Put(...)`。
- `apps/backend/src/idempotency-store.ts`：`Put` 同步写临时 JSON 并重命名，写盘异常直接向上抛出。
- `apps/backend/src/host.ts`：每次 `Command` 自动生成新的内部 `requestId`，超时或失败后的调用方重试无法复用原幂等键。

最小复现结果：

```json
{
  "executions": 2,
  "first": { "ok": false, "error": { "code": "STORAGE_ERROR" } },
  "second": { "ok": false, "error": { "code": "STORAGE_ERROR" } }
}
```

复现条件：使用合法写通道，业务方法成功返回，但注入的 `idempotencyStore.Put` 模拟磁盘不可用并抛出 `STORAGE_ERROR`；以同一 `requestId` 连续调用两次。结果业务方法执行两次，两次响应均报告失败。

影响：

- 设置保存、附件清理、实体写入等通道可能出现“客户端看到失败，但副作用已经发生”。
- 用户或 UI 按失败响应重试时，可能重复增加 revision、重复写审计、重复执行非天然幂等操作。
- 当前 Host 不允许上层提供稳定幂等键，跨超时、Backend 重启与 UI 重试的持久化幂等目标实际上无法兑现。

根因：幂等结果记录位于业务副作用之后，且独立 JSON 文件不在业务事务中；缓存持久化失败被 Router 的统一 `catch` 归一为整次命令失败。同时，请求幂等键由 Host 每次调用临时生成，未覆盖真实重试边界。

整改要求：

1. 先补失败用例，再改实现；至少覆盖“业务成功 + 幂等记录失败”“同键并发”“同键不同 payload”“Backend 重启后重放”和“超时后重试”。
2. 明确幂等事实源和事务边界。优先让业务写入与幂等状态共享可原子提交的持久化边界；若分阶段迁移，必须保证不会向调用方返回可重试失败后又重复副作用。
3. 让稳定幂等键从真实调用方重试边界进入信封，并与内部追踪 `requestId` 分离；禁止继续把每次自动生成的 requestId 同时当作跨重试幂等键。
4. 保持凭据与敏感 payload 不进入回放存储；错误结构仍须稳定且可追踪。

验收标准：上述用例全部自动化通过；连续重试、并发重复请求和 Backend 重启场景中，业务副作用次数均为 1；磁盘异常时响应语义与实际业务状态一致。

当前只有构建记录、契约抽查和单次 Electron 冒烟，无法验证 revision、幂等、补偿、脱敏及 Worker 崩溃恢复等高风险路径。此项与既定 B-03 一致，但 R-01 的回归用例不应等待完整测试体系结束；后端开发应在 R-01 中先建立最小可运行测试入口，再由 B-03 扩展。
