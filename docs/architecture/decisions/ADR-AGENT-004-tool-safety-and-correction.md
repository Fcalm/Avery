# ADR-AGENT-004：工具安全、确认与有界纠正

> 状态：已接受
>
> 决策日期：2026-08-20
>
> 实现授权：已授权；A-03 安全边界与三档确认权限已实施

## 上下文

Provider 对工具 Schema 的支持程度不同，模型参数与确认文本都不可信。长时间持锁会阻塞用户编辑；只用 `Promise.race` 会产生超时后仍写入的幽灵副作用；无限让模型修正会掩盖协议或权限错误。简历允许合理包装，但推测性补全必须由用户确认后才能进入正式版本。

## 决策

1. 内部工具 Schema 使用受限 JSON Schema 2020-12 子集：顶层 object、写工具 `additionalProperties: false`、有限深度/长度；禁用远程引用、递归和 Provider 语义不一致的复杂组合。
2. Schema 只验证形状。Harness 继续校验场景白名单、资源归属、revision、风险、确认和数据范围；Backend 窄端口再次鉴权。
3. 等待确认期间保存规范参数、proposal hash、diff 和 expected revision，不持有资源锁。接受时重新读取、加锁并校验 revision，只执行冻结提案。
4. 写工具在执行前记录持久化 Tool Ledger，使用业务幂等键；生产 Host 未提供持久化 Ledger 时拒绝写入，不退化为内存保证。
5. 每个工具获得可取消 `AbortSignal` 和 deadline。写入超时且结果无法证明时记为 `status_unknown`，先对账再决定是否重放。
6. 同一错误指纹最多允许模型纠正 1 次。Provider 瞬时错误只在尚未输出正文、尚未执行工具时有界退避，并遵守 `Retry-After`。
7. 确认权限分为 `always_confirm`、`allow_low_risk` 和 `fully_trusted`。它们只改变已授权动作的确认方式；进入 `fully_trusted` 前 UI 必须警告并由用户显式确认，且不能扩展白名单或资源权限。
8. 含 `【待确认】` 的简历草稿必须进入等待文本确认，即使使用 `fully_trusted` 也不能直接写入。

## 替代方案

- **完全依赖 Provider strict schema**：不能证明权限和业务语义，否决。
- **为 Preview/Commit 分别暴露模型工具**：增加模型选择歧义；确认阶段由 Harness 管理，不采用。
- **等待期间持锁**：崩溃或长等待会阻塞用户，否决。
- **超时后直接重试写入**：可能重复副作用，否决。
- **多轮自我反思直到通过**：无界且会掩盖根因，否决。

## 影响

正面影响：

- 用户看到的提案与真正执行参数一致。
- 写入可跨重启对账，超时不会自动产生第二次提交。
- 工具契约可跨 Provider 下编译而不牺牲运行时安全。

负面影响：

- 确认恢复、Ledger 和对账增加实现复杂度。
- 某些可修复输出在一次纠正后仍会暂停，需要用户介入。
- `fully_trusted` 不能免除推测事实确认，交互步骤会增加。

## 迁移

1. 建立 Schema 方言 lint 与 Adapter fixture。
2. 将确认提案和待确认简历草稿持久化到 Run，等待前释放锁。
3. 强制注入持久化 Ledger、AbortSignal、deadline、actor 和 authorization ID。
4. 将 A-01 的白名单、超时、待确认草稿失败用例逐项转为普通回归。

## 回退

若新调度或确认路径出现问题，回退时禁用对应写工具并保留只读能力；不得恢复长时间持锁、内存幂等或超时后盲目重试。已冻结提案保持只读并标记过期，用户可在修复后创建新提案。
