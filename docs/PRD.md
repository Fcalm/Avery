## 1. 文档目的

本文定义 Avery 的产品定位、最终能力边界、核心流程、跨模块规则和验收标准。

- 本文回答“产品为什么做、为谁做、必须做到什么”。
- 各模块的字段、界面、状态机、协议和实现细节由专项文档定义。
- 专项文档不得削弱本文规定的权限、安全、隐私、数据一致性和用户控制要求。
- 本文与旧文档冲突时，以本文确认的产品方向为准；架构与实施仍需遵守现行 `AGENTS.md`。

## 2. 产品定义

### 2.1 产品定位

Avery 是面向校招学生的本地优先 AI 求职桌面应用，围绕“建立真实求职档案—生成针对性简历—完成授权投递—持续跟踪结果”形成闭环。

产品的两个核心价值是：

1. **简历优化**：把分散的个人经历和代码项目整理为结构化事实，由 Agent 按岗位要求生成、修改和维护针对性简历。
2. **自动化投递**：在用户设定目标、规则和权限后，自动完成受支持页面中的信息填写、材料选择、检查和提交，并保留可追踪记录。

面试准备属于次要能力，服务于投递后的跟进，不应挤占简历和投递主流程。

### 2.2 目标用户

主要用户为正在参加校招、实习招聘或毕业初期招聘的学生，典型特征包括：

- 求职经验较少，不清楚如何把课程、竞赛、实习和代码项目转化为岗位相关成果。
- 需要为不同岗位反复调整简历，但缺少稳定的事实资料和版本管理。
- 面对重复的申请表单、附件上传和进度记录，时间成本高且容易漏填、错填或重复投递。
- 重视个人资料、简历、代码和模型凭据的隐私，希望数据优先保存在本机。

### 2.3 产品形态与基础约束

- 首发平台为 Windows 桌面端。
- 基准窗口为 1280×800，最低可用窗口为 1024×680。
- 单机、单用户、单工作空间；当前不建设 Avery 云端账号和云同步。
- 用户自备模型服务 API Key，凭据仅加密保存在本机。
- 不默认上传产品使用数据、崩溃报告或行为遥测。

## 3. 产品目标与非目标

### 3.1 产品目标

- 用户可以用一套可信档案持续生成多份针对不同岗位的简历。
- Agent 对简历的修改是结构化、可预览、可撤销、可追踪的，不以整篇文本覆盖作为常规编辑方式。
- 用户可以从岗位库发起受控的自动化投递，并随时暂停、确认、接管或终止。
- 会话、项目环境、模型状态、Usage 和投递记录在重新进入后准确恢复。
- 业务数据、凭据、附件和可观测性信息具有清晰的本地边界和恢复能力。

### 3.2 非目标

- 不提供社交社区、招聘方后台或企业招聘管理系统。
- 不提供虚构经历、伪造证明或绕过申请真实性校验的能力。
- 不绕过验证码、反自动化机制、登录安全验证或平台明确的访问限制。
- 不提供岗位匹配分或自动岗位评分；现有界面中的占位匹配分应移除或隐藏。
- 不以自动抓取全网岗位作为当前核心入口；当前以手动录入为主，后续支持从用户提供的 URL 提取。
- 不在没有用户配置的情况下把图片发送给任何外部视觉服务。

## 4. 产品原则

1. **事实优先**：简历内容必须能追溯到用户档案、项目材料或用户明确输入，不得把模型推断写成事实。
2. **用户可控**：高影响操作必须提供清晰状态、权限、暂停、接管、确认和撤销能力。
3. **结构化编辑**：Agent 通过模块级操作修改简历，避免不可解释的整篇替换。
4. **本地优先**：能在本地完成的数据管理、版本、日志和审计不得无理由上传。
5. **最小授权**：场景决定 System Prompt 与工具白名单；目录、平台和操作权限不得跨场景继承扩大。
6. **真实可观测**：用户界面使用 Provider 返回的真实 Usage；缺失时显示未知，不用估算值冒充。
7. **失败可恢复**：自动化、迁移、保存和 Agent 运行失败后必须可重试、接管或回到稳定状态。

## 5. 核心用户旅程

### 5.1 首次建立求职工作空间

1. 用户完成首次启动向导并设置昵称。
2. 用户配置文本模型服务并通过连接测试。
3. 用户填写求职类型、学历、经验、行业、目标岗位和城市。
4. 系统建立本地工作空间，将非敏感求职偏好写入档案库。
5. 用户导入或新建基础简历，并补充项目、实习、教育和技能资料。

### 5.2 针对岗位生成简历

1. 用户手动录入岗位与完整 JD；后续版本可从 URL 提取。
2. 用户进入求职助手，选择简历场景、目标岗位、当前简历和可选项目环境。
3. Agent 读取授权范围内的档案、简历和项目文件，识别缺失事实并向用户提问。
4. Agent 生成模块级修改方案；根据权限模式等待确认或保存为新版本。
5. 用户预览结构化简历，必要时手工调整并导出。

### 5.3 自动化投递

1. 用户在岗位库选择一个或多个有有效申请入口的岗位。
2. 用户选择投递模式、目标简历、申请规则和每日上限。
3. 系统执行投递前检查，展示缺失资料、风险项和预计操作。
4. 自动化引擎填写表单、选择答案、上传材料并处理可恢复错误。
5. 遇到未知字段、低置信度、敏感问题、验证码或平台限制时暂停并请求用户接管。
6. 提交成功后自动创建或更新投递记录，并保存时间、岗位、简历版本、关键答案和结果凭证。

### 5.4 投递后跟进

1. 用户在投递管理中查看已收藏、已投递、笔试、面试和结束阶段。
2. 用户记录下一步日期、备注和进度。
3. 次要的面试能力可基于 JD、简历和档案生成准备清单，但不改变核心事实数据。

## 7. 功能需求

### 7.1 首次启动与设置

- 向导收集昵称、求职类型、经验阶段、最高学历、行业、最多三个目标岗位和求职城市。
- 支持 DeepSeek 与 OpenAI-compatible 自定义文本模型服务。
- API Key 必须先通过连接测试，再由桌面端安全存储；表单草稿和业务数据库不得保存明文 Key。
- 向导中断后恢复到最近步骤，但不恢复 API Key 明文。
- 设置支持修改账户昵称、会话自定义上下文、模型、压缩阈值、工作空间和开发者选项。
- 工作空间迁移采用“复制—校验—切换”，原目录保留；Agent 运行时禁止迁移。

### 7.2 档案库

档案库保存用户确认过的事实材料，分类至少包括项目经历、工作/实习经历、教育背景、技能证书和其他资料。

- 支持新增、编辑、删除、分类浏览和关键词搜索。
- Agent 可以在授权场景中只读引用档案；写入或修正事实必须由用户确认。
- 档案项应保留稳定 ID、更新时间和版本信息，外部修改冲突时禁止静默覆盖。
- 求职偏好属于档案的一部分，可被简历和投递流程引用。

具体字段、证据关联和冲突处理由档案模块文档定义。

### 7.3 结构化简历

#### 7.3.1 数据结构

简历由稳定、可排序的模块组成，而不是仅保存一段不可区分的全文。基础模块至少包括：

- 基本信息与求职意向。
- 个人总结。
- 教育经历。
- 实习或工作经历。
- 项目经历。
- 技能与证书。
- 用户自定义模块。

每个模块和条目必须具有稳定 ID、类型、顺序、结构化字段、展示内容和来源信息。模块文档负责定义完整 Schema。

#### 7.3.2 Agent 编辑规则

- Agent 只能通过模块级命令新增、修改、删除或重排内容，不得把整份简历作为无结构字符串直接覆盖。
- 每次修改必须指明目标模块、变更前后内容、依据和涉及的档案/项目来源。
- Agent 不得自行补造公司、时间、成果数字、技术栈或职责；证据不足时必须提问。
- “需要确认”模式下，任何写入都必须先展示差异并等待用户确认。
- “无需确认”模式下，可以自动写入，但必须生成新版本并保留修改记录，不得破坏用户可回退的上一版本。
- 用户和 Agent 编辑同一简历时使用同一资源锁与 revision 校验，冲突时停止写入并提示选择最新版本。

#### 7.3.3 版本与导出

- 支持多份简历，并指定当前供助手和投递使用的简历。
- 用户修改、Agent 修改、导入和恢复均生成明确来源的版本。
- 普通历史版本至少保留最近 100 个；用户标记的重要版本永久保留，除非用户主动删除。
- 支持导入现有 PDF 和 Word 简历，并转换为结构化模块；无法可靠识别的字段必须交由用户确认。
- 支持导出 PDF、Word 和图片；导出必须由用户界面主动发起。
- 投递记录必须固定引用实际提交时的简历版本，后续编辑不得改变历史投递材料。

### 7.4 求职助手与 Agent

#### 7.4.1 会话

- 支持多个独立会话，保存标题、可见消息、思考展示内容、附件引用和更新时间。
- 新会话在发送第一条有效消息时创建。
- 支持流式回复、停止生成、失败重试、重载会话和历史恢复。
- 切换会话后必须立即恢复该会话独立的 Usage、项目环境、模型和必要状态，不得复用其他会话数据。
- 运行中状态必须区分生成、等待用户回答、等待写入确认、自动化执行、已暂停、已取消、完成和失败。

#### 7.4.2 场景

“场景”不是页面导航，而是 Agent 的能力配置。切换场景必须同时改变：

- System Prompt。
- 可用工具白名单。
- 可读取的数据范围。
- 写操作和确认策略。
- 推荐输入和结果展示方式。

首批场景至少包括简历优化、岗位定制简历、项目经历提炼和投递辅助。面试准备作为次要场景后续加入。

场景切换不得让工具权限累加；每次运行只使用当前场景的最小工具集合。场景的 Prompt 与工具清单由 Agent 模块文档定义。

#### 7.4.3 权限模式

- 默认模式为“需要确认”。
- 用户可以切换为“无需确认”，该选择按会话保存并在界面中持续可见。
- “无需确认”只免除该场景内已授权低风险写操作的逐次确认，不得跳过目录授权、外部服务授权、自动提交规则或安全拦截。
- 删除、覆盖不可恢复内容、扩大文件范围、发送图片到外部视觉服务等高风险操作始终需要单独确认。
- 权限控件在窄输入区只显示统一图标，并保留可访问名称和状态提示。

#### 7.4.4 提问、任务与附件

- Agent 需要补充信息时，以结构化问题请求用户选择或填写；未回答完整前不得假设事实继续写入。
- 长任务显示当前目标、步骤状态和可停止入口。
- 支持导入文本、PDF、Word 和常见图片附件；源文件进入受控工作空间后只通过虚拟引用访问。
- 解析失败必须说明原因和可处理格式，不能把空解析结果当作成功。

### 7.5 项目环境

项目环境用于读取用户授权的代码项目，提炼可验证的项目经历，不是通用文件系统入口。

#### 7.5.1 授权边界

- 用户必须主动选择项目目录；项目按会话独立绑定并在重新进入后恢复。
- 默认只读，Agent 不得修改、创建、删除或执行项目文件。
- 系统先生成可读取文件清单供用户查看，再把最小必要内容提供给 Agent。
- 文件范围同时遵守 `.gitignore`、内置排除规则、文件类型限制、单文件大小和总读取量限制。

#### 7.5.2 强制排除

无论场景如何配置，默认不得读取：

- `.env` 及其变体、凭据文件、私钥、证书、Token、密码库和云服务配置。
- `.git` 内部数据、依赖目录、构建产物、缓存、数据库、日志和大型二进制文件。
- 被用户明确排除的路径。

疑似敏感内容应停止读取并提示用户，而不是自动上传给模型。用户可以缩小授权范围，但不能通过普通场景关闭核心敏感规则。

#### 7.5.3 项目经历提炼

- Agent 应优先读取 README、依赖清单、公开配置和用户指定源码。
- 输出需区分“文件中可确认的事实”“根据代码推断的结论”和“需要用户补充的成果”。
- 不能仅凭技术依赖推断用户职责、团队规模或业务成果。
- 写入简历前必须映射到结构化项目模块，并保留来源引用。

### 7.6 岗位库

- 当前支持手动录入公司、岗位、城市、薪资、经验、用工类型、渠道、申请 URL 和完整 JD。
- 支持编辑、收藏、删除以及按收藏和渠道筛选。
- 后续支持由用户提供 URL 后提取岗位信息；提取结果必须预览确认后入库。
- 不自动扫描全网岗位，不计算岗位匹配分。
- 岗位删除前应提示对现有投递记录的影响；历史投递至少保留必要岗位快照。

### 7.7 自动化投递

自动化投递是核心能力，但“自动填写”和“自动提交”必须分级，避免错误材料、错误答案、重复投递和账号风险。

#### 7.7.1 投递来源与前置条件

- 自动化从用户岗位库中的明确申请 URL 发起，不在未授权情况下自主发现或抓取岗位。
- 岗位、目标简历版本、基础档案和必填求职偏好必须完整。
- 用户需完成对应平台登录；Avery 不读取或导出用户密码。
- 每次投递任务必须记录平台、岗位、规则、简历版本、启动人和权限模式。

#### 7.7.2 投递模式

1. **辅助投递（默认）**：系统完成识别、填写、材料上传和校验，在最终提交前由用户确认。
2. **全自动投递（高级）**：用户对具体平台或投递批次显式启用，配置岗位过滤、答案规则、每日上限和可自动提交范围；仅在所有检查通过且置信度达标时提交。

启用“无需确认”的简历权限，不等于启用全自动投递。两种授权必须分开保存和展示。

#### 7.7.3 自动填写规则

- 优先使用用户档案中的结构化事实和已确认的标准答案。
- 根据岗位选择用户指定或规则允许的简历版本，不得在提交时临时改写已冻结文件。
- 表单字段必须记录来源、填写值和置信度。
- 未知字段不得猜测；可选字段可按规则留空，必填字段必须暂停请求用户处理。
- 涉及身份、工作许可、薪资、地域意愿、诚信声明、隐私授权等敏感问题时，必须使用用户预先确认的答案；没有答案则暂停。

#### 7.7.4 强制暂停条件

出现以下任一情况时，系统必须暂停，不得尝试绕过：

- 验证码、短信/邮箱验证、二次认证或反自动化挑战。
- 页面结构无法识别、字段语义冲突或必填项置信度不足。
- 实际岗位与岗位库信息明显不一致。
- 申请需要新声明、测评、录制音视频、签署协议或支付费用。
- 发现可能重复投递、超过用户限额或平台返回风险提示。
- 登录失效、账号受限、页面要求人工接管或平台禁止继续自动操作。

#### 7.7.5 提交、幂等与审计

- 投递任务具有唯一 ID，同一岗位、账号和投递批次不得因重试产生重复提交。
- 提交前执行最终校验：岗位、公司、简历版本、附件、关键答案和提交模式。
- 成功后保存时间、结果状态、页面回执或可用凭证，并更新投递管理。
- 失败后区分可重试、需接管、已拒绝和状态未知；状态未知时禁止自动再次提交。
- 用户可以查看自动化步骤和关键填写记录，暂停、继续、接管或终止任务。
- 提供全局停止开关；停止后不得继续页面操作或排队提交。
- 不绕过平台限制，不以隐藏浏览器行为、伪造设备或规避检测作为产品能力。

支持平台、页面适配器、字段置信度和限速策略由自动化投递专项文档定义。

### 7.8 投递管理与面试辅助

- 投递阶段至少包括已收藏、已投递、笔试中、面试中和已结束。
- 记录关联岗位快照、实际简历版本、投递日期、下一步日期、备注和不可变状态事件。
- 自动化投递成功后自动建档；人工投递可以手动新增。
- 支持推进阶段、修改日期和删除记录，删除前说明对审计记录的影响。
- 面试辅助可生成岗位分析、问题清单和复习重点，但不得修改投递事实或简历历史版本。

### 7.9 外挂多模态视觉服务

当主文本模型不支持视觉时，Avery 可调用用户单独配置的多模态模型解析图片，再把结构化结果提供给文本模型。

- 用户必须单独填写并测试视觉服务 API Key；文本模型 Key 与视觉 Key 不得默认共用。
- 首次向视觉服务发送图片前展示服务名称、图片数量和数据用途并取得确认。
- 未配置视觉服务时，图片理解功能显示不可用；不回退到本地 OCR，也不假装解析成功。
- 只发送用户选择的图片和最小必要提示，不发送整个工作空间、无关档案或代码目录。
- 视觉结果必须标记来源和不确定性；涉及简历事实时仍需用户确认。
- API Key、原图和视觉响应遵循本地凭据、附件和 Trace 脱敏规则。

### 7.10 Usage、上下文压缩与 Trace

#### 7.10.1 用户 Usage

- 每个会话独立保存 Usage；进入会话时立即恢复，不能等下一次请求后才显示。
- 百分比固定为最近一次已完成请求的 `prompt_tokens / context_limit`。
- 详情仅展示 `prompt_tokens`、`context_limit` 和当前压缩阈值等必要具体数值，不显示累计消费图表或估算值。
- Usage 以 Provider 返回为准；Provider 未返回时显示“未知”，不得用字符数或本地估算冒充真实 Usage。
- 新会话在尚无成功请求时显示“—”，不是 0%。

#### 7.10.2 压缩规则

- Usage 展示指标与压缩管道的预判指标必须分开：界面展示上一请求的真实值，管道在下一请求前使用上下文构建器的 token 预算判断是否压缩。
- 压缩阈值可配置为 1%–80%，默认值由专项文档确定。
- 压缩必须保留 System Prompt、当前场景工具定义、关键事实、未完成任务、最近对话和必要引用。
- 压缩后必须保留可追踪的摘要版本与压缩次数；不得因压缩改变用户事实或权限。

#### 7.10.3 开发者 Trace

- Trace 与求职助手读取同一份 Provider Usage 事实记录，不重复估算。
- Trace 可保存 Provider 返回的完整 Usage 字段供排障，但普通用户界面保持简洁。
- Trace、日志和请求内容仅保存在本机，写入前移除 API Key、Authorization、疑似凭据和不必要的绝对路径。
- 开发者模式关闭后不新增 Trace；用户可配置保留数量并一键清空。

### 7.11 本地数据、备份与恢复

- 会话、简历、岗位、投递和设置使用本地业务数据库；档案、附件、导出和备份位于受控工作空间。
- API Key 只允许存在于表单短期内存和系统安全存储，不进入业务数据库、日志、Trace 或导出包。
- 所有可变实体使用 revision 或等价机制检测外部修改冲突。
- 数据库迁移前创建备份；迁移、文件写入或数据库提交失败时执行补偿，不得留下半完成业务状态。
- 启动时检查工作空间和数据库完整性；损坏或未知高版本 Schema 时进入恢复/只读状态。
- 用户可手动创建备份；自动备份至少保留最近 7 份。
- 无引用附件延迟清理，默认保护期 30 天；清理不得删除仍被会话、简历或投递引用的文件。
- 默认不上传遥测、崩溃报告和使用分析。用户主动导出诊断包时，应先预览范围并再次脱敏。

## 8. 全局交互要求

- 关键操作必须具备 loading、empty、error、success、冲突和恢复状态。
- 发送、停止、确认、暂停和保存等主操作在最低窗口宽度下保持可见且不畸变。
- 求职助手输入区根据实际可用宽度切换紧凑模式；隐藏文本后保留图标、可访问名称和工具提示。
- 会话侧栏的编辑、切换和设置控件固定在底部，不随列表滚动消失。
- 对话区与输入区使用一致的最小宽度；侧栏拖动到极限时不得反向撑大输入框。
- 标题区控制高度，正文和输入区优先获得垂直空间；输入框下方不放置长期占位提示文本。
- 所有删除、覆盖、迁移、清空和自动提交操作提供与风险匹配的确认信息。
- 核心流程支持键盘操作，焦点状态清晰，图标按钮提供可访问名称。

## 9. 权限与安全模型

| 资源或能力 | 默认权限 | 可扩展方式 | 不可突破的边界 |
| --- | --- | --- | --- |
| 档案与简历读取 | 当前场景内只读 | 用户选择目标数据 | 不读取未授权工作空间 |
| 简历写入 | 需要确认 | 会话内启用无需确认 | 自动写入仍生成新版本 |
| 项目环境 | 用户选定目录只读 | 缩小到子目录/文件 | 不执行、不写入、不读敏感文件 |
| 视觉图片 | 不发送 | 用户配置 Key 并逐次/规则授权 | 不静默上传或本地 OCR 回退 |
| 自动填写 | 投递任务内授权 | 平台/批次规则 | 未知事实不得猜测 |
| 自动提交 | 默认最终确认 | 显式启用高级模式 | 验证码、敏感问题和风险状态必须暂停 |
| 简历导出 | 用户界面触发 | 选择格式和位置 | Agent 工具不得直接导出 |
| 日志与 Trace | 本地、脱敏 | 用户开启开发者模式 | 不上传、不记录凭据 |

权限判断必须在执行端再次校验，不能只依赖前端按钮是否可见。

## 10. 非功能要求与保守指标

由于产品不上传遥测，下列指标通过本地自动化测试、发布前基准测试和用户自愿参与的可用性测试验证，不得为测量而新增静默数据上传。

### 10.1 可用性指标

- 至少 70% 的目标测试用户无需人工指导即可完成“引导—档案—结构化简历—岗位—投递”核心路径。
- 在资料已准备的前提下，首次生成一份可审阅的岗位定制简历中位时间不超过 30 分钟。
- 核心错误必须提供下一步操作，不能仅显示技术错误或要求重启。

### 10.2 Agent 与简历指标

- 结构化编辑命令在标准测试集中的正确应用率不低于 95%。
- 未经授权的简历写入、目录读取、工具调用和事实编造验收结果必须为 0。
- 停止请求后 1 秒内进入已停止或正在停止的可见状态；迟到事件不得覆盖其他会话。
- Provider 未返回 Usage 时，错误显示为真实值的次数必须为 0。

### 10.3 自动化投递指标

- 对明确列入支持范围的页面，标准字段自动填写准确率不低于 90%。
- 在无验证码、页面未变化且资料完整的基准场景中，投递流程完成率不低于 80%。
- 重复提交、越过每日上限、未经授权提交和状态未知时自动重试的次数必须为 0。
- 用户点击全局停止后，不再启动新的页面操作或提交动作。

### 10.4 性能与稳定性指标

- 基准设备冷启动至可交互首页 P95 不超过 5 秒。
- 本地页面切换和常规表单反馈 P95 不超过 200 毫秒。
- 1280×800 与 1024×680 下核心控件无遮挡、无横向功能丢失和拖动畸变。
- 发布前稳定性测试中无数据丢失；备份、迁移失败回滚和损坏库恢复用例通过率 100%。
- 主进程和渲染进程不得因模型、数据库或自动化长任务而持续阻塞。

### 10.5 隐私与安全指标

- 测试日志、Trace、诊断包和业务导出中的 API Key/Authorization 泄漏为 0。
- 未经授权的外部网络请求、文件读取和图片上传为 0。
- 安装、升级和卸载不得默认删除用户工作空间。

## 11. 发布与验收门禁

一个版本只有同时满足以下条件才可标记为可发布：

1. 安装、首次启动、升级、卸载保留数据和重新安装验证通过。
2. 首次引导、模型连接、档案、简历、会话、岗位、投递和备份主路径通过。
3. 结构化简历编辑、确认/无需确认、版本回退和冲突路径通过。
4. 自动化投递的辅助模式、全自动规则、暂停接管、停止、幂等和审计路径通过。
5. Provider 成功、认证失败、超时、取消、重试和 Usage 缺失路径通过。
6. 项目环境敏感文件排除、路径逃逸和读取上限测试通过。
7. 视觉服务未配置、授权发送、失败和不确定结果路径通过。
8. 工作空间迁移、备份恢复、损坏库和未完成操作补偿演练通过。
9. 1280×800、1024×680 和关键拖动边界的视觉回归通过。
10. API Key、敏感文件、日志和 Trace 脱敏安全测试通过。

无法验证的关键门禁必须在发布报告中明确列出，不能以“代码已完成”代替产品验收。

## 12. 分阶段交付

本文描述最终产品目标，允许按风险分阶段开放：

- **基础闭环**：本地工作空间、档案、结构化简历、求职助手、岗位库和投递管理。
- **受控投递**：先开放少量平台的辅助投递，再通过专项验收开放全自动模式。
- **增强输入**：URL 岗位提取、外挂视觉服务和更完整的简历导入。
- **次要能力**：面试准备与投递后的辅助分析。

分阶段交付不得把尚未通过安全和幂等验收的自动提交包装为可用功能。
