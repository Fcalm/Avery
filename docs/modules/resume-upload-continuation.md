# 简历上传后的对话恢复

## 现象与证据

2026-11-09，“你好”会话最近两次网申请求分别在北京时间 15:39:20 和 15:41:16 开始，均在确认上传之后报 `The attachment URI is invalid.`。两次使用 ego lite 和 `mimo-v2.6-flash`。

只读核对业务消息、Trace 以及运行历史后确认：两个请求的上传工具均已返回 `status:succeeded`、`uploaded:true`、`readyForFill:true`，随后在恢复模型请求的准备阶段失败。错误本身不是上传失败的证据，不应据此重传简历。

第二次“继续”属于新请求，曾尝试复用前次的临时文件 ID，工具正确返回未授权，随后重新导出再上传；之后仍触发相同的恢复错误。检查期间没有重新操作用户网站、投递或修改真实业务数据。

## 复现与根因

1. 使用支持图片输入的模型进入工作场景，读取并绑定简历。
2. `ExportResumeFile` 返回 `asset://resume/<UUID>`，工具把它加入本 Run 的附件授权列表，以允许后续上传。
3. 在需要确认的模式下调用 `BrowserUploadFile`，宿主将该列表保存到等待点的 `input.attachments`。
4. 用户批准后上传成功；恢复同一个 Run 时，宿主把混入导出文件的列表重新送入 `CreateVisionUserMessage`。
5. 该函数经业务附件端口解析 URI，端口只接受 `attachment://<ID>/<文件名>`，因而拒绝 `asset://resume/...`，中断已完成动作之后的模型续轮。

该混用存在于 AgentHost，支持视觉输入的模型配合任一浏览器均可能触发；并非 ego 原生上传协议特有错误。导出的 PNG 同样可能触发。

## 修复

- 将原用户附件与工具可用的附件授权分为独立副本，导出不再污染原始消息。
- 等待点的 `input.attachments` 只记录原用户附件，另用 `authorizedAttachments` 保存同一 Run 的导出授权，支持连续确认与续轮。
- 视觉输入只处理原用户附件；已存在的图片仍按原引用和哈希完整重放，损坏或缺失时继续阻断，不静默丢图。
- 兼容旧等待记录：只在恢复旧记录时分离 Host 导出 URI；普通新请求的附件校验保持严格。
- 未找到内存授权的导出 ID 不再送入业务附件解析器，而返回文件不可用 / 未授权。重启后临时导出授权仍须重新取得，不通过识别 URI 猜测文件路径。

原有会话、任务、提案、页面与文件绑定，以及上传确认和回执去重继续生效。恢复不会再次执行已经结算的上传。

## 验证

新增真实附件 Worker 与正式 AgentHost 集成场景，在修复前四项均稳定复现原始 URI 错误，修复后通过：PDF、PNG、原用户图片与导出文件并存、旧格式等待记录。每项覆盖两个不同附件框的连续确认，检查各动作仅执行一次、用户消息唯一、原图片内容不变、续轮授权保留及等待点落盘字段。

相关 7 个文件、123 项 Vitest 检查，以及 14 项后端 Node 检查通过；`npm run build:packages` 的类型检查和构建通过。

浏览器操作与模型输出使用隔离端口，不连接真实网站或线上模型；不以此宣称已经重新完成用户的网申。重启 Avery 后应先观察当前表单，确认已上传状态再继续填写，避免仅因旧错误提示重复上传。
