# 简历场景资料包

本包包含两套相互独立的中文求职任务，每套 3 题。每题使用不同人物资料，均与目标岗位有实质关联，也保留真实求职中常见的经历不足、表达不准确或结果验证缺口。

## 使用文件

每套目录含：

- `dataset.jsonl`：逐行独立案例，可直接导入 Prompt 项目。
- `rubric.md`：与该套案例配套的评分说明，导入时一并使用。
- `rubric-dimensions.json`：六个评分维度的 ID、名称及权重；用于项目的维度配置。

`materials` 含两份完整 JD、三份完整简历及三份完整档案，便于人工阅读。运行所需内容已经完整内嵌在 JSONL，不依赖 URL、登录状态、本机原始 JD 文件或这些辅助 Markdown 的磁盘路径。

匹配场景通过绑定简历提供原文，JD 放在项目文件中；编写场景通过档案条目提供事实，另放一份同内容的完整 Markdown，便于按自然文档阅读。副本不构成第二份经历，人数和项目不能重复累计。

## 项目配置

1. 为两套资料分别建立 Prompt 项目，执行模型与 Judge 模型从本机已配置供应商中选择。两套应使用各自 rubric，不混用。
2. 导入该套 `dataset.jsonl`，同时加载对应 `rubric.md`。
3. 在评分配置中按 `rubric-dimensions.json` 填入六个 ID、名称和权重，合计 100。仅导入 rubric 文字不会自动改变默认四维；该 JSON 是配置对照文件，当前界面没有将其一键导入的入口。
4. 工具选 `Read`、`Glob`、`ReadResume`、`ReadProfile` 即可；无需浏览器或写工具。最大轮数建议 12，重复次数建议 3，交互策略保留 `approve_valid`，开启严格 JSON 输出。此处的配置属于项目执行设置，不写进用户请求。
5. 使用当前生产提示词作为初始候选。先确认逐题有正文、证据和判定，再比较不同候选；Judge 或供应商失败单列，不把未计分当零分。

本轮交付分析与内容编写，不包含持久化编辑或投递流程。每题附有 `expectedState`，要求档案与简历保持原值，以及禁止写入操作的约束。匹配判断允许合理分数或区间，不预设唯一答案；编写任务要求成稿，不以模板或一般建议代替。

## 信息隔离

被执行模型可见的用户请求、绑定简历、档案条目、文件名和文件正文均使用自然求职表达，不出现评估用途标记。JSONL 的 `expected`、参考答案和 rubric 仅供 Judge 使用；不得复制到 `fixtures.files` 或用户消息，也不要把本说明、整个资料包目录或评分文件作为求职者附件发送。

本包没有增加任何告知执行模型其所处评估环境的提示。现有 Runner 仍会产生内部会话、工程和路径标识；本轮不变更该基础设施，不承诺对运行环境指纹做匿名化处理。
